状态：Active

SQLFlow 文档分成事实源、派生指南和生成内容。写文档前先判断信息属于哪一层，避免在多个文件维护同一事实。

## 事实源

| 问题 | 事实源 | 内容边界 |
|------|--------|----------|
| 产品必须做什么 | [需求文档](REQUIREMENTS.md) | 角色、范围、功能需求、质量属性、状态机和验收标准 |
| 系统当前如何组织 | [架构文档](ARCHITECTURE.md) | 运行时、模块边界、依赖方向、数据与安全约束 |
| 为什么这样设计 | [ADR](adr/README.md) | 难以逆转且存在真实取舍的架构决策 |
| HTTP 契约是什么 | Handler 注解生成的 OpenAPI | 方法、路径、参数、响应和认证要求 |

需求描述目标，架构描述当前结构，ADR 解释关键决定。三者发生冲突时，不应靠复制文字修补：先确认产品目标，再新增或更新 ADR，最后同步架构和实现。

## 生成内容

- `internal/api/openapi/docs.go` 由 `make docs` 生成，不手工编辑。
- 服务启动后通过 `/swagger/index.html` 浏览 API 文档。
- 构建、测试和覆盖率报告属于 CI 产物，不进入现行规范。

## 推荐阅读路径

- 第一次了解项目：项目 README → 需求 → 架构 → ADR。
- 开发产品功能：相关需求 → 架构模块 → 对应 ADR → 代码与测试。
- 修改基础设施：架构 → ADR → 配置与编排文件。
- 修改界面：需求 → 前端架构 → 前端开发说明。
- 排查线上问题：健康探针/日志 → Swagger 或代码。

## 维护规则

1. `docs/` 中的需求、架构和派生文档只描述当前有效内容，不保存版本流水账。
2. 难以逆转、非显而易见且存在真实取舍的决定进入 ADR；普通实现细节不写 ADR。
3. 新接口更新 handler 注解并运行 `make docs`，不在 README 中复制端点表。
4. 功能变更至少检查需求、权限、状态机和审计影响。
5. 架构边界、存储、部署或集成方式变化时，先更新或新增 ADR，再更新架构与运维文档。
6. 示例命令必须可以复制执行；环境变量名称以 `config/config.go` 的 `envBindings` 为准。
7. 文档使用仓库相对链接，提交前运行文档校验。

## 元数据约定

事实源文档在标题后记录状态、维护者、最后评审日期和相关代码。状态使用：

- `Draft`：尚未成为有效约束。
- `Active`：当前有效。
- `Deprecated`：仍可查阅但不应继续采用。
- `Superseded`：已由明确的新文档或 ADR 替代。
