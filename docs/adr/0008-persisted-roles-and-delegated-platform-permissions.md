# ADR-0008：持久化角色与可委派平台权限

- 状态：accepted
- 日期：2026-07-30
- 决策者：Team
- 关联需求：FR-IAM-003、FR-IAM-006、FR-SEC-001、FR-SEC-005
- 取代：无
- 被取代：无

## 背景

SQLFlow 最初把 `admin`、`dba`、`developer` 写死在 Service、Handler 和前端选项中。Casbin 虽然可以保存任意主体策略，但系统没有角色实体、生命周期、成员保护或平台管理权限，导致自定义策略无法形成可管理的完整角色。

## 决策

1. 使用平台 SQLite 中的 `roles` 表保存角色标识、显示名称、描述、内置标记和状态。
2. `admin`、`dba`、`developer` 作为受保护的内置角色迁移进入该表；内置角色不可停用或删除。
3. 角色标识创建后不可修改，避免用户引用、Casbin 主体和审批链发生非原子重命名。
4. 有成员的角色不可停用或删除；删除自定义角色时原子删除其 Casbin 策略。
5. 数据权限继续使用 `角色/用户、数据源域、对象、动作` 元组。
6. 平台管理权限使用 `角色、system、平台资源、动作` 元组，可委派用户、RBAC、数据源、安全、审计和设置管理能力。
7. JWT 请求使用数据库中的当前用户角色重新鉴权；API Token 同时要求其所有者角色仍有效，因此角色调整或停用即时生效。
8. API Token Scope 仍只能收窄 RBAC 权限，不能独立扩大平台权限。

## 备选方案

- 继续使用固定角色：实现简单，但无法满足不同团队、环境和职责分离要求。
- 只允许创建 Casbin 主体而不建立角色表：缺少生命周期、成员统计、在用保护和可审计元数据。
- 允许角色重命名：需要同时迁移用户、策略、审批链、SLA 和历史记录，失败恢复复杂，因此暂不支持。

## 后果

- 管理员可以创建自定义角色，并分别授予平台管理权限和数据对象权限。
- 用户创建、角色调整、审批链校验和权限策略选择统一读取有效角色。
- 每次 JWT 请求增加一次当前用户与角色有效性读取，以换取角色变更即时生效。
- 业务服务不得新增基于任意自定义角色名称的硬编码判断；应使用 Casbin 权限或审批阶段要求。

## 验证

- Migration 验证内置角色与既有自定义策略主体被保留。
- Service 测试覆盖角色 CRUD、内置保护、在用保护和策略清理。
- Handler 与前端构建验证角色 API、动态选择器和管理页面。
- 中间件测试验证平台权限允许受委派角色并拒绝未授权角色。
