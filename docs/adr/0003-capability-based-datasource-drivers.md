## 背景

MySQL、PostgreSQL、MongoDB 和 Elasticsearch 在查询语法、事务、元数据、字段脱敏和批量执行上存在本质差异。通过类型分支散落在 Service 中会使新增驱动和安全审查越来越困难；强迫所有驱动表现为完全一致又会掩盖真实限制。

## 决策

定义统一 `Driver` 接口，并要求驱动显式声明查询、工单执行、元数据、表级权限、字段脱敏、解析和导出能力。驱动通过注册表按类型创建，由 `PoolManager` 按数据源 ID 管理生命周期。上层依据能力选择流程或返回明确的不支持错误。

## 备选方案

- 每种数据源独立 Service/API：能体现差异，但会复制认证、权限、审计和 UI 流程。
- 最小公共接口配合大量类型断言：接口简单，但差异仍会泄漏到业务层。
- 强制完整同构接口：表面统一，但容易用空实现或不安全降级伪造能力。

## 后果

- 优点：能力差异显式；新增驱动有稳定扩展点；连接生命周期统一。
- 代价：Service 在迁移期仍需处理少量类型特有路径；接口演进影响全部驱动。
- 约束：不得把未支持能力静默降级为成功；事务语义必须在驱动和产品文档中明确。

## 验证

- `internal/driver/driver.go` 定义接口和 `CapabilitySet`。
- 各驱动包注册类型并提供单元测试。
- 查询、数据源和工单 Service 使用能力或适配层访问目标数据源。
